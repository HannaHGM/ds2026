# 2.2 Exercises: git with a copy somewhere else

Practice for session 2.2. Everything here needs the internet and a GitHub account.

**Do each exercise twice where it makes sense: once at the terminal, once in GitStudio.** Some
of these only exist on github.com.

Keep working in your own `ds2026` repository, the one you initialised in 2.1.

Answers are at the bottom. Try first.

---

## 1. Somewhere to push to

On github.com, create a **new, empty, private** repository called `ds2026`. Do not let it add
a README, a `.gitignore` or a licence: it has to be empty, or your first push will be
rejected.

Copy the HTTPS URL it shows you.

**Terminal.** Ask your repository which remotes it knows about. Add the GitHub one, calling
it `origin`. Ask again.

**Check.** The second answer has two lines, both the same URL. Why two?

---

## 2. The first push

**Terminal.** Push `main` to `origin`, setting it as the branch's upstream.

If a browser window asks you to sign in to GitHub, accept it. If it asks for a password in
the terminal, stop: that has not worked since 2021, and the prep tells you what to do instead.

**Check.** Refresh the GitHub page. Three things to look for:

- every commit you made in 2.1 is listed, not just the latest
- `.gitignore` is there
- `data/` and anything in it is **not**

---

## 3. What never left your laptop

**Terminal.** Ask git whether it has ever recorded anything about your `.venv` folder, or a
file inside `data/`.

**Check.** The answer is nothing at all, and that is the point: ignored files are not hidden
from GitHub, they were never committed in the first place. Now list what is being ignored, so
"ignored" does not mean "invisible to you".

---

## 4. Invite the people who need to see it

**On GitHub.** Settings → Collaborators → Add people. Invite the module staff, whose usernames
are on Canvas.

**Check.** A private repository that nobody can read is as good as no submission. This is the
step people forget in Week 7.

---

## 5. A change that happens somewhere else

**On GitHub.** Open `README.md` in the browser, click the pencil, add a line, and commit it
directly on `main`.

Now your laptop is out of date and does not know it.

**Terminal.** Ask GitHub what is new, without changing any of your files. Then check your
status.

**GitStudio.** The graph now shows your branch and `origin/main` in different places.

**Check.** Your status says you are behind by one commit. Is the new line in your local
README yet? Look at the file before you answer.

---

## 6. Fetch and pull are different

**Terminal.** Now bring the change in properly.

**Check.** In one sentence each: what did `fetch` do, and what did `pull` add to it?

---

## 7. The everyday loop

Do a full cycle, in order, saying out loud what each step is for:

1. bring down anything new
2. make a change and save it
3. stage it
4. commit it with a message someone could read
5. send it up

**Check.** Which of those five steps is the one people skip, and what goes wrong when they do?

---

## 8. Two people, one line

This is the situation that makes people afraid of git, so do it on purpose, in a repository
that does not matter.

**On GitHub.** Edit the second line of `README.md` in the browser and commit it.

**On your laptop.** Without pulling, edit the same line differently, and commit.

**Terminal.** Pull.

You get a conflict, and git stops. Open the file: your version and theirs are both there,
between `<<<<<<<`, `=======` and `>>>>>>>`.

**Resolve it.** Delete the markers, leave the text you want, stage the file, commit, push.

**Check.** Who decided what the final line says? Not git. What would have happened if you had
pulled before you started editing?

---

## 9. A copy of the copy

**Terminal.** Somewhere outside your `ds2026` folder, clone your own repository from GitHub
into a folder called `ds2026-clone`.

**Check.** Three questions:

- does it have your full history, or only the latest version?
- does it have a remote already set up, and what is it called?
- is `data/` in it? Why not?

Delete the clone when you have answered. It has done its job.

---

## 10. Someone else's repository

**On GitHub.** Fork the class practice repository of someone at your table, which makes
your own copy of it under your account.

**Terminal.** Clone **your fork**, make a small change on a new branch, commit, push the
branch.

**On GitHub.** Open a pull request from your branch back to the original repository.

**Check.** How many repositories were involved, and where does your commit live now?

---

## 11. What happens when you commit a secret

Imagine you commit a file with an API key in it and push. Ten minutes later you delete the
file, commit, and push again.

**Terminal.** Prove to yourself whether the key is still in the repository, using `git log`
on the file path.

**Check.** Is deleting enough? What do you have to do in real life, and why does "it was a
private repo" not help?

---

## 12. Put it together, no hints

1. Make a branch called `readme-fix`, improve one line of `README.md`, and push the branch to
   GitHub.
2. Open a pull request from `readme-fix` into `main`, on your own repository.
3. Merge it on GitHub.
4. Get the merge back onto your laptop.
5. Delete the branch, locally and on GitHub.

---

# Answers

**1.** `git remote -v`, `git remote add origin <url>`, `git remote -v`. Two lines because git
keeps the fetch URL and the push URL separately. They are normally the same, and they do not
have to be.

**2.** `git push -u origin main`. `-u` sets `origin/main` as the upstream, which is what lets
you type plain `git push` and `git pull` afterwards.

**3.** `git log -- .venv` and `git log -- data/` both return nothing: no commit ever touched
them. `git status --ignored` lists what is being skipped.

**5.** `git fetch`, then `git status`. The line is **not** in your file yet. Fetch updates
git's picture of the remote, and touches nothing in your working directory.

**6.** `git pull`. Fetch downloads; pull downloads and then merges into your branch. `pull` is
`fetch` plus `merge`.

**7.** `git pull`, edit, `git add <file>`, `git commit -m "..."`, `git push`. The skipped step
is the first one: pull before you start. Skipping it is what turns a two-second merge into
exercise 8.

**8.** After resolving: `git add README.md`, `git commit`, `git push`. You decided, not git.
Git stops precisely because it cannot know which line is right. Pulling first would have meant
editing the already-updated line, with no conflict at all.

**9.** `git clone <url> ds2026-clone`. Full history; `origin` already configured; no `data/`,
because it was never committed, so there is nothing to clone.

**10.** Three: the original, your fork on GitHub, and your clone on disk. Your commit is on a
branch in your fork, and the pull request is a request that the original repository take it.

**11.** `git log --oneline -- path/to/file` still lists the commit that added it. Deleting
removes it from the latest snapshot and not from history. In real life: revoke the key and
issue a new one. Private does not help, because everyone with access can still read it, and
repositories get made public by accident.

**12.** `git switch -c readme-fix`, edit, `git add README.md`,
`git commit -m "Clarify how to get the data"`, `git push -u origin readme-fix`, open and merge
the PR on GitHub, then `git switch main`, `git pull`, `git branch -d readme-fix`, and
`git push origin --delete readme-fix`.
